# ANDROID_CONTRACT.md — обмен AshCRM ↔ приложение для Android · версия **1.7** (2026-11-13)

Единственный источник правды для обмена между CRM (`crm-ashbyte`) и приложением для Android
(`crm-ashbyte-android`, пакет `ru.ashcrm.app`, далее — **приложение**). Одна и та же копия лежит в обоих репозиториях:
`crm-ashbyte/docs/contracts/ANDROID_CONTRACT.md` и `crm-ashbyte-android/docs/ANDROID_CONTRACT.md`.

Что для этого нужно сделать в CRM — задание в репозитории CRM.

**Как менять** — как `NOTIFY_CONTRACT.md`: правка, касающаяся приложения, начинается с этого файла, версия
поднимается, изменение описывается в §10, копия кладётся в оба репозитория.
* **Минорная версия** (1.0 → 1.1) — только добавления. Приложение игнорирует незнакомые поля, виды и коды.
* **Мажорная версия** (1.x → 2.0) — несовместимо. Приложение с другой мажорной версией **обязано обновиться**
  (§2): экран «Обновите приложение» без кнопки «Позже».
* Константы: CRM — `AndroidContract` (рядом с `realtime.NotifyContract`); приложение — `BuildConfig.CONTRACT`
  (`app/build.gradle.kts`).

---

## 1. Общее

* Адрес портала `<CRM>` вводит пользователь при первом запуске: схема и хост, без пути. `http://` — только для
  адресов локальной сети и этого устройства (как `NOTIFY_CONTRACT` §1).
* REST — `<CRM>/api/v1`, JSON UTF-8, время RFC 3339, ошибки `{"error": {"code", "message"}}` — как `NOTIFY_CONTRACT` §1.
* Приложение подписывает **каждый** свой запрос и WebView заголовком
  `User-Agent: … AshCRM-Android/<версия> (Android <версия ОС>; contract <X.Y>)`. В WebView это дописка в конец
  обычного User-Agent браузера. По метке `AshCRM-Android/` CRM узнаёт, что страница открыта в приложении (§7).

## 2. Версия приложения и обновление (с 1.2 — из релизов; с 12.11 — GitVerse)

Решение владельца (10.11): одна CRM, одно приложение, много пользователей — версии и APK приложение берёт из
релизов репозитория `crm-ashbyte-android`, CRM сообщает только версию контракта. С 12.11 (приложение 0.5.0)
релизы — на GitVerse `AshByte/crm-ashbyte-android` (до этого — GitHub `AshByteDev/crm-ashbyte-android`).

### 2.1. `GET /app/android` (CRM) — без авторизации
`200 {"contract": "1.2"}` — CRM знает приложение; остальные поля (с 1.0) приложение с 1.2 не читает.
`404` с JSON-ошибкой — CRM не поддерживает приложение: оно работает как оболочка PWA, без уведомлений.
`GET /download/ashcrm.apk` (CRM) — `302` на `url` из `android.json` (§2.2) — файл последнего выпуска
`https://gitverse.ru/api/attachments/<uuid>` (у GitVerse нет постоянной ссылки «последний выпуск»). CRM читает
`android.json` не чаще раза в 5 минут; GitVerse не ответил — последняя известная ссылка, а если её ещё нет — страница
релизов `https://gitverse.ru/AshByte/crm-ashbyte-android/releases`. Ссылка и QR-код из CRM ведут на последний выпуск.

### 2.2. `android.json` релиза
`https://gitverse.ru/api/repos/AshByte/crm-ashbyte-android/raw/branch/main/release/android.json` — файл в ветке
`main` (на частые запросы GitVerse отвечает 429 — приложение молча ждёт и повторяет). До 12.11 —
`https://github.com/AshByteDev/crm-ashbyte-android/releases/latest/download/android.json`.
```json
{"version_code": 3, "version_name": "0.3.0", "min_version_code": 1, "contract": "1.2",
 "sha256": "<hex SHA-256 APK>", "size": 2058746,
 "url": "https://gitverse.ru/api/attachments/afd5ec5f-4c46-4cd1-9ef9-0c66f3275fc9",
 "notes": ["…", "…"]}
```

### 2.3. Правила приложения
| Условие | Что делает приложение |
|---|---|
| GitVerse не ответил | ничего; проверит при следующем запуске |
| своя версия < `min_version_code` | экран «Обновите приложение», **без отказа** |
| мажорная версия контракта CRM ≠ своей и в релизах есть версия новее | экран «Обновите приложение», без отказа; уведомления не регистрируются |
| мажорная версия CRM ≠ своей, новее версии нет | «Версии не совпадают», CRM работает в WebView, уведомлений нет |
| `version_code` больше своего | диалог «Доступна версия X» с «Что нового» **один раз**; «Позже» — до следующего `version_code` |

Проверка — при запуске и не чаще раза в 6 часов, пока приложение открыто; CRM спрашивается заново при каждом
возврате, пока не ответила или не знала приложение. APK скачивается только по ссылке релиза этого репозитория
(`https://gitverse.ru/api/attachments/…`, только `gitverse.ru`); файл проверяется по `sha256` и сертификату подписи (тот же, что у установленного приложения).

## 3. Подключение устройства

Пароль, 2FA и вход остаются в CRM. Повторно входить не нужно: страница подключения открывается **в WebView
приложения**, где сотрудник уже вошёл или входит сейчас. Это вариант `NOTIFY_CONTRACT` §2, где вместо loopback
приложение перехватывает переход на свою схему.

1. Приложение создаёт `verifier`, `challenge`, `state` (как `NOTIFY_CONTRACT` §2) и открывает в своём WebView
   ```
   <CRM>/desktop-connect?app=android&challenge=<challenge>&state=<state>&device=<устройство>
   ```
   `device` — `<производитель> <модель>` (`Xiaomi 23078PND5G`), до 60 символов.
2. Страница (вход — если нужен) спрашивает «Подключить уведомления на этом телефоне?» и по «Подключить» вызывает
   `POST /auth/desktop/authorize` с `{"challenge", "device", "app": "android"}`, затем переходит на
   ```
   ashcrm://connect?code=<code>&state=<state>
   ```
   По «Не сейчас» — `ashcrm://connect?cancel=1&state=<state>`.
3. Приложение перехватывает этот адрес внутри своего WebView (во внешний мир он не уходит), сверяет `state` и
   меняет код: `POST /auth/desktop/token` (§3.2 `NOTIFY_CONTRACT`) → `DesktopTokens`.
4. CRM создаёт сессию вида **`android`** с именем `Android · <device>`; прежняя сессия с тем же именем у этого
   сотрудника завершается (переустановка).

С 1.4 (решение владельца 12.11) телефон подключается **без вопроса**: приложение открывает адрес шага 1 с
`&auto=1`, и страница сразу, без «Подключить уведомления на этом телефоне?», переходит на `ashcrm://connect?code=…`.
Приложение делает это само после **любого** входа на странице (мост `login`, §7.1: пароль, вход по QR §3.4) и при
запуске, если сотрудник вошёл, а телефон не подключён. «Не сейчас» больше нет.

Обновление ключа — `POST /auth/desktop/refresh`, как `NOTIFY_CONTRACT` §3.3 (ключ обновления одноразовый, `401` —
подключить заново, `409` — повторить через секунду). Время жизни ключей — как `NOTIFY_CONTRACT` §3.4.

### 3.1. Что открывает ключ приложения
| Запрос | Зачем |
|---|---|
| `GET /me` | имя сотрудника и компании на экране настроек |
| `POST /auth/logout` | «Отключить уведомления» |
| `POST /push/subscriptions`, `DELETE /push/subscriptions` | регистрация устройства (§4) |
| `POST /push/test` | «Проверить уведомления» на экране настроек |
| `POST /notify/read` `{"key": "…"}` → `{"ok": true}` | кнопка «Прочитано» в уведомлении; смысл — как кадр `notify.read` (`NOTIFY_CONTRACT` §5.5) |
| `POST /auth/app/web-code` → `{"code": "…"}` | с 1.1: вход страницы по сессии устройства (§3.2) |

Остальное — `403`. С 1.1 (запасной канал без Google) ключ откроет и WebSocket `notify.*`, как у приложения Windows.

### 3.2. Вход страницы по сессии устройства (с 1.1)

Сотрудник вводит пароль **один раз** — при подключении телефона. Сессия устройства (`android`) живёт 30 дней с
продлением при каждом обновлении ключа, её ключ обновления хранится в Android Keystore телефона и не привязан к IP.
Если страница CRM в приложении осталась без входа (cookie потеряна, сессия страницы завершена), приложение открывает
её этой сессией, а не просит пароль.

1. Страница пришла на `/login`, телефон подключён, сотрудник **не** нажимал «Выйти» (мост `logout`, §7.1) —
   приложение вызывает `POST /auth/app/web-code` (ключ `android`) → `200 {"code": "<одноразовый>"}`.
   Код живёт **60 секунд**, сгорает при первой попытке, привязан к сессии устройства.
2. Приложение открывает в WebView `GET <CRM>/api/v1/auth/app/web-login?code=<code>` (без авторизации; путь под
   `/api/`, чтобы Service Worker не подменил его страницей). CRM создаёт **веб-сессию того же сотрудника**
   (`client = 'web'`, имя `Android · <device> (страница)`), связанную с сессией устройства, ставит обычную cookie
   обновления (как при входе) и отвечает `302` на `/`.
3. Код неверен, устарел или использован, сессия устройства завершена, учётная запись заблокирована —
   `302` на `/login?app_login=failed`: обычная форма входа. Приложение пробует не чаще раза в минуту.
* 2FA повторно не спрашивается: она пройдена при подключении телефона.
* Завершение сессии устройства (выход, «Мои устройства», блокировка) завершает и её веб-сессии.
* `404` на `/auth/app/web-code` — CRM 1.0: приложение показывает обычную форму входа.

### 3.3. Ключ телефона и подписанное обновление (с 1.3)

Вход привязан к **самому телефону**, а не к IP или сети: при подключении приложение создаёт пару ключей P-256 в
Android Keystore (в защищённом чипе, если он есть). Закрытый ключ из телефона извлечь нельзя.

* `POST /auth/desktop/token` — дополнительно `"device_key": "<base64url SubjectPublicKeyInfo>"`: CRM сохраняет его
  у сессии `android`.
* `POST /auth/desktop/refresh` — дополнительно `"device_key"` (тот же), `"device_ts"` (unix-секунды) и
  `"device_sig"`: base64url DER-подписи ECDSA P-256 / SHA-256 текста
  ```
  ashcrm-refresh\n<refresh_token>\n<device_ts>
  ```
* У сессии есть ключ → подпись **обязательна**: нет, неверна или `device_ts` дальше ±10 минут — `401`.
  У сессии ключа ещё нет (подключена до 1.3) → ключ из первого обновления с верной подписью сохраняется.
* **Повтор с верной подписью** — предъявлен уже сменённый ключ обновления этой сессии (потерялся ответ в мобильной
  сети, приложение выгрузили до записи) — **не кража**: CRM выдаёт новую пару, сессию не закрывает. Без верной
  подписи повтор — как раньше (сессия закрывается).
* Срок сессии — прежний: 30 дней с последнего обновления. Приложение само обновляет ключ раз в сутки, когда есть
  сеть, — сессия не истекает, пока телефон хоть раз в 30 дней бывает в сети.

### 3.4. Вход по QR-коду (с 1.4)

Схема — `docs/QR_LOGIN.md` CRM. QR всегда показывает компьютер, сканирует всегда телефон. Код в QR — адрес:
```
<CRM>/qr#in.<token>     — войти на компьютере: телефон, где сотрудник вошёл, подтверждает
<CRM>/qr#out.<token>    — войти на телефоне: телефон без входа входит, компьютер подтверждает
```
Весь вход (ожидание подтверждения, код 2FA) делает **страница `/qr` в WebView**; приложение только сканирует и
открывает адрес.

1. **Сканер** — свой, на экране приложения (камера, `CAMERA` спрашивается при первом сканировании). Принимается
   только QR-код с адресом вида `http(s)://<хост>[:<порт>]/qr#in.…` или `…/qr#out.…`, остальное — «Это не код входа
   AshCRM», сканер остаётся открытым.
2. **Экран адреса портала** (первый запуск или «Сменить портал»): кнопка «Вход по QR». Портал берётся из кода
   (схема, хост и порт; правила §1 — `http://` только для локальной сети). Приложение спрашивает «Подключиться к
   `<хост>`?», сохраняет портал как введённый вручную и открывает в WebView адрес из кода.
3. **Страница CRM** (форма входа, меню профиля) вызывает сканер мостом `{t: "scan"}` (§7.1). Код с тем же
   `<CRM>` — приложение открывает его адрес в своём WebView. Код другого портала — «Код другого портала: <хост>»,
   ничего не открывается.
4. После входа страница шлёт мост `login` — приложение подключает уведомления телефона (§3, `auto=1`).

### 3.5. Разрешение на уведомления (с 1.4)

После подключения (§3) без разрешения `POST_NOTIFICATIONS` (Android 13+) или с выключенными уведомлениями
приложения приложение **не спрашивает, а сообщает**: экран «Для работы нужны уведомления» с одной кнопкой
«Разрешить», которая сразу вызывает системный запрос. Отказ — тот же экран с «Открыть настройки» (системные
настройки уведомлений приложения) и «Позже» (до следующего запуска).

## 4. Регистрация устройства

`POST /push/subscriptions` (ключ приложения):
```json
{"endpoint": "fcm:<токен FCM>", "p256dh": "<base64url, 65 байт>", "auth": "<base64url, 16 байт>", "platform": "android"}
```
* `p256dh` и `auth` — ключи шифрования **приложения** (P-256 и секрет), как у подписки браузера (RFC 8291).
  Закрытый ключ не покидает телефон.
* Подписка привязана к сессии приложения. Завершение сессии (выход, «Мои устройства», `401` при обновлении) удаляет
  её подписки.
* Токен FCM сменился — приложение удаляет старый `endpoint` и регистрирует новый. Запрос повторяется при каждом
  запуске: CRM обновляет существующую запись (`endpoint` уникален).

## 5. Доставка

Для подписки с `endpoint` `fcm:<токен>` CRM вместо Web Push отправляет **сообщение FCM HTTP v1 только с данными**:
```json
{"message": {"token": "<токен>",
  "data": {"p": "<base64url без = : тело aes128gcm>"},
  "android": {"priority": "HIGH", "ttl": "86400s", "collapse_key": "<topic(tag)>"}}}
```
* `p` — **то же содержимое, что у веб-пуша** (`{"type","title","body","url","tag","clear"}`, с 1.5 — ещё `"alert"`, с 1.6 — `"category"`, с 1.7 — `"call_kind"`), зашифрованное по
  RFC 8291 (`aes128gcm`, одна запись, минимальное дополнение) ключами `p256dh`/`auth` подписки. Google видит только
  шифротекст.
* Размер: webpush-go по умолчанию дополняет тело до 4096 байт (5462 символа `p`) — **больше предела FCM в 4 КБ**.
  CRM шифрует с `RecordSize: 2700`: тело всегда ровно 2700 байт, `p` — **3600 символов** (проверено webpush-go v1.4.0
  против приложения). Одинаковая длина заодно не выдаёт длину текста. На открытый JSON остаётся до **2597 байт**:
  длинный `body` CRM обрезает (по символам, с «…») до шифрования.
* `priority`: `HIGH` — для всего, что показывается (карточки, проверка); `NORMAL` — для `type: "clear"`. FCM понижает
  приоритет приложению, которое шлёт `HIGH` без видимого уведомления.
* Блок `notification` не передаётся: уведомление строит приложение.
* Ответ FCM `404 UNREGISTERED` или `400 INVALID_ARGUMENT` про токен — подписка удаляется (как `404/410` веб-пуша);
  `429`/`5xx` — сбой подписки, повтор по общим правилам.

### 5.1. Содержимое (`p` после расшифровки)
| `type` | Что показывает приложение |
|---|---|
| `dm`, `groups`, `mentions` | канал «Сотрудники» |
| `mine`, `queue`, `alerts` | канал «Клиенты и очередь» |
| `call` | канал «Звонки» — заметное уведомление со звуком, без полноэкранного режима |
| `tasks`, `calendar`, `policy` | канал «Задачи и встречи» |
| `test` | канал «Служебные» |
| `delivery` | с 1.5: канал «Доставка» — **свой звук** (отличный от остальных каналов; водители и сотрудники, получающие уведомления доставки). С `"alert": true` — канал «Доставка — важное»: всплывающее уведомление, звук погромче и вибрация (пинг диспетчера, «Не удалось», «Срок прошёл», срочная заявка, «Поставили раньше заявки в работе», «Водитель снят») |
| `clear` | убрать уведомления с ключами `clear` (прочитано в другом месте) |
| незнакомый | как `dm` |

* `tag` — ключ карточки (`NOTIFY_CONTRACT` §5.4): новое уведомление с тем же `tag` **заменяет** прежнее.
* `url` — путь в CRM; нажатие открывает `<CRM> + url` в приложении. Абсолютные адреса приложение не открывает.
* Кнопка «Прочитано» есть у ключей `chat-`, `task-`, `event-`, `channel-`, `queue-`, `alert-`, `missedcall-`, с 1.5
  `delivery-` → §3.1.
* С 1.5 `alert` (bool, нет — `false`) — заметное уведомление; сейчас бывает только у `delivery`, у других видов
  приложение его не учитывает.
* Пока приложение на экране, уведомление показывается без звука (звук и всплывашки даёт сама страница CRM).

| `delivery` | доставка | `truck` | `#0E8F86` |
| `alert` | системное предупреждение | `triangle-alert` | `#D93B30` |

* **Маленький значок** (status bar, `setSmallIcon`) — форма из таблицы, векторная (vector drawable из lucide,
  одноцветная по правилам Android). **Цвет** — `setColor` цвета категории. **Большой значок** (`setLargeIcon`) —
  белая форма на круге цвета категории; готовые PNG 192×192: `GET <CRM>/icons/notify/<category>.png` (статический
  файл, без авторизации) — можно положить их в приложение или нарисовать те же формы.
* **Текст** приходит уже без служебных слов: у пропущенного звонка и очереди `title` — клиент (имя или номер), у
  группы — название группы, `body` — суть («3 новых · Мария: …»). Приложение ничего не дописывает в `title`.
* **Группа уведомлений** приложения (сводка нескольких): каждая строка начинается со значка категории (или точки её
  цвета, если значок в строке не помещается); текст сводки — по категориям: «5 уведомлений: 2 звонка, 2 клиента,
  1 коллега». Пропущенные звонки и сообщения одного клиента не склеиваются в одну строку.
* `alert: true` — по-прежнему заметное уведомление (§5.1) поверх цвета категории.

#### 5.2.1. Трубка звонка: `call_kind` (с 1.7)

`call_kind` (string, нет поля — не звонок) — событие **телефонный звонок** этого вида. В `body` слова «Входящий /
Исходящий / Пропущенный звонок» нет («2:35 · 08. Ремзона · на смене: …»): приложение показывает трубку — в начале
текста (span с vector drawable) или, если так нельзя, символом цвета вида. Вид решает CRM по схеме звонков, текст
приложение не разбирает.

| `call_kind` | Значок (lucide) | Цвет |
|---|---|---|
| `in` — входящий | `phone-incoming` | `#2EAD5B` |
| `out` — исходящий | `phone-outgoing` | `#3390EC` |
| `missed` — пропущенный | `phone-missed` | `#D93B30` |
| `dropped` — сброс | `phone-off` | `#8A8F98` |
| `spam` — спам | `phone-incoming` | `#F97316` |
| `ringing` — идёт звонок | `phone-call` | `#2EAD5B` |
| незнакомое значение | `phone-call` | `#8A8F98` |

## 6. Правила доставки на телефон

Подписка `android` — это «Мобильные» (`NOTIFICATIONS_PLAN.md`): задержка, проверка «прочитано», «за компьютером»,
выключатель «Мобильные», рабочий день — всё как сейчас, без отдельных правил.

## 7. Страница CRM внутри приложения

Метка `AshCRM-Android/` в User-Agent означает:
* Вкладка приложения — это **телефон**, а не компьютер: она не делает сотрудника «за компьютером» для отложенных
  пушей на телефон (иначе телефон молчал бы 5 минут после сворачивания приложения).
* Веб-пуш внутри WebView не работает: карточку «Включите уведомления» и подписку браузера не показывать; в
  «Настройки → Уведомления» — «Уведомления приходят через приложение» и кнопка «Настройки приложения» (§7.1).

### 7.1. Мост страница → приложение
Только на `<CRM>` (приложение принимает сообщения лишь от этого origin):
```js
window.AshCRMAndroid?.postMessage(JSON.stringify({t: "settings"}))  // открыть настройки приложения
window.AshCRMAndroid?.postMessage(JSON.stringify({t: "logout"}))    // сотрудник вышел — отключить уведомления устройства
window.AshCRMAndroid?.postMessage(JSON.stringify({t: "login"}))     // вошёл — приложение подключает уведомления (§3, с 1.4 без вопроса)
window.AshCRMAndroid?.postMessage(JSON.stringify({t: "scan"}))      // с 1.4: открыть сканер QR входа (§3.4)
```
`logout` — до перехода на страницу входа. Незнакомые `t` приложение игнорирует.
Кнопки «Вход по QR» страница показывает в приложении только с `contract` ≥ 1.4 в User-Agent (§1).

### 7.2. Геолокация для страницы (с 1.5)
Водитель «Доставки» отмечает точки, и страница CRM в этот момент один раз спрашивает местоположение
(`navigator.geolocation.getCurrentPosition`, `docs/DELIVERY_PLAN.md` §13.1). WebView отдаёт его странице так:
* `WebChromeClient.onGeolocationPermissionsShowPrompt(origin, callback)`: только для `origin` портала `<CRM>`; иначе —
  `callback.invoke(origin, false, false)`.
* Разрешение Android (`ACCESS_FINE_LOCATION` и `ACCESS_COARSE_LOCATION` в манифесте) запрашивается **в этот момент**
  (первая отметка), а не при запуске приложения. Дал хотя бы приблизительное — `callback.invoke(origin, true, false)`.
  Отказал — `false`: страница сохраняет отметку «без геолокации» и сама подсказывает, как включить.
* «Больше не спрашивать» — `false` без системного окна; кнопка «Настройки приложения» (мост `settings`, §7.1) ведёт
  в системные настройки, где разрешение включается.
* **Только в момент запроса страницы**: фоновой геолокации нет (`ACCESS_BACKGROUND_LOCATION` не нужен, служб нет).
* Страница ждёт ответа не дольше 10 секунд и сохраняет отметку в любом случае.

### 7.3. Камера в выборе файла (с 1.5)
Водитель прикладывает к отметке фото «с камеры» (`<input type="file" accept="image/*" capture="environment">`).
* `onShowFileChooser`: если среди `acceptTypes` есть `image/*` (или `image/…`) — системный выбор с пунктом **«Камера»**
  (`MediaStore.ACTION_IMAGE_CAPTURE`, снимок во временный файл через `FileProvider`) рядом с галереей и файлами;
  `params.isCaptureEnabled()` — сразу камера.
* Разрешение `CAMERA` — в момент выбора «Камера». Отказ — выбор без камеры, как сейчас.
* Снимок отдаётся странице как обычный выбранный файл (`content://`), временный файл удаляется после загрузки.
* Голосовое к отметке записывает сама страница (микрофон, как сейчас для голосовых в чатах, `RECORD_AUDIO`).

### 7.4. Карты и Навигатор (с 1.5)
Карточка заявки даёт ссылки (`docs/DELIVERY_PLAN.md` §14.2): `yandexnavi://build_route_on_map?lat_to=…&lon_to=…`
(Яндекс Навигатор) и `https://yandex.ru/maps/?…` (Яндекс Карты).
* Обе уходят **наружу** (`Intent.ACTION_VIEW`), как другие ссылки не на `<CRM>`; `https://yandex.ru/maps/` откроется в
  приложении Яндекс Карты, если оно есть, иначе в браузере.
* Нет приложения для `yandexnavi://` — короткое сообщение «Установите Яндекс Навигатор или откройте «Карты»» (сейчас
  — «Нет приложения, чтобы открыть ссылку»).

## 8. Требования к приложению (безопасность)
* Ключ обновления и закрытый ключ шифрования хранятся зашифрованными ключом Android Keystore; ключ телефона (§3.3) создаётся в Keystore и не извлекается; в журналы не пишутся.
* `state` сверяется; схема `ashcrm://` перехватывается только внутри своего WebView.
* Открывается только `<CRM> + url`; ссылки на другие сайты — во внешнем браузере.
* Обновление — только APK из релиза этого репозитория, с тем же сертификатом подписи и совпавшим `sha256`.

## 9. Проверка совместимости
* Приложение: юнит-тесты (`./gradlew test`) — расшифровка по тестовому вектору RFC 8291, правила версий.
* CRM: интеграционный тест канала FCM на поддельном сервере FCM (как `push_integration_test.go`).
